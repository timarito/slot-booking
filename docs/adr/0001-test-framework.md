# ADR 0001: тестовый фреймворк — Vitest

- Статус: принято
- Дата: 2026-11-18

## Контекст

В стеке (`CLAUDE.md` §4) тестовый фреймворк для API был оставлен открытым: Jest или Vitest. Нужно
решить до первых тестов, потому что от выбора зависят конфиги, моки и CI.

Факты о проекте, которые влияют на решение:

- API — нативный ESM (`"type": "module"`, `module: nodenext`), как генерирует NestJS 12.
- Фронтенд (`apps/web`) по стеку тестируется Vitest.
- NestJS DI зависит от `emitDecoratorMetadata`: тестовый трансформер TypeScript обязан генерировать
  метаданные декораторов, иначе DI в тестах не работает.
- Шаблон `nest new` в NestJS 12 по умолчанию генерирует проект с Vitest.

## Решение

Используем **Vitest** для unit- и e2e-тестов API.

- Unit-тесты: `apps/api/src/**/*.spec.ts`, конфиг `vitest.config.ts`, без БД и сети.
- E2E-тесты: `apps/api/test/**/*.e2e-spec.ts`, конфиг `vitest.config.e2e.ts`, поднимают весь
  `AppModule` и ходят в реальный Postgres.
- Импорты `describe/it/expect/vi` — явные из `vitest`, без глобальных переменных.

## Альтернативы

**Jest** — самый распространённый выбор для NestJS: зрелый, огромная экосистема, большинство статей и
старых шаблонов Nest написаны под него. Отклонён, потому что:

- поддержка ESM в Jest до сих пор экспериментальная (запуск через `--experimental-vm-modules`),
  а наш API — нативный ESM. Пришлось бы либо компилировать тесты в CommonJS, либо жить с флагом;
- для TypeScript нужен отдельный трансформер (`ts-jest` или `@swc/jest`);
- на фронтенде всё равно будет Vitest — два фреймворка с похожим, но не одинаковым API
  (`jest.fn` vs `vi.fn`, разные конфиги) только добавляют когнитивную нагрузку.

**Node.js test runner (`node:test`)** — без зависимостей, но нет удобных моков модулей, watch-режима
уровня Vitest и экосистемы; TypeScript с декораторами всё равно потребовал бы отдельной сборки.

## Последствия

- Один тестовый инструмент на весь монорепо, общий опыт и конфиги.
- Проверено на практике: трансформер Vitest 5 генерирует метаданные декораторов — DI
  (`HealthController` без `@Inject()`) работает в тестах без `unplugin-swc`.
- Полифил `reflect-metadata` в приложении неявно загружает `@nestjs/core`. Unit-тесты, которые не
  импортируют Nest, его не получают, поэтому он подключён через `setupFiles` в `vitest.config.ts`.
- `vite` — peer-зависимость Vitest 5 и указан в `devDependencies` явно.
- Риск: если будущая версия Vitest/Vite сменит трансформер и перестанет генерировать метаданные
  декораторов, тест `health.controller.spec.ts` упадёт первым — это и есть наш сигнал. Решение
  в этом случае — `unplugin-swc`.
- E2E-тесты требуют запущенного Postgres и `apps/api/.env`. В CI переменные окружения будут
  передаваться явно (задача CI).
