# slot-booking — функциональная спецификация

Статус: черновик v1 (2026-11-18). Источник истины для бизнес-правил. Изменения правил вносятся через PR,
который обновляет этот файл.

Маркеры объёма работ, используемые в документе:

- **[MVP]** — обязательно для v1.0 (вехи M2–M5).
- **[Post-MVP]** — целевое состояние, запланировано после v1.0. Перечислено, чтобы дизайн MVP его не блокировал.

---

## 1. Глоссарий

| Термин                        | Значение                                                                                         |
| ----------------------------- | ------------------------------------------------------------------------------------------------ |
| Ресурс (Resource)             | То, что можно забронировать: переговорная или рабочее место.                                     |
| Часовой пояс ресурса          | IANA-зона (например, `Europe/Berlin`), в которой заданы рабочие часы ресурса.                    |
| Рабочее окно (working window) | Интервал `[open, close)` ресурса в одну локальную календарную дату.                              |
| Шаг слота (slot step)         | Гранулярность сетки бронирования (15, 30 или 60 мин). Бронь начинается и заканчивается на сетке. |
| Слот                          | Одна ячейка сетки `[t, t + step)` внутри рабочего окна.                                          |
| Бронь (Booking)               | Резервирование одного ресурса одним пользователем на период `[startAt, endAt)`.                  |
| Активная бронь                | Бронь со статусом `confirmed`, у которой `endAt` в будущем.                                      |
| Сейчас (now)                  | Серверное время. Часам клиента в бизнес-правилах никогда не доверяем.                            |

Все периоды **полуоткрытые** `[start, end)`: бронь `10:00–11:00` и бронь `11:00–12:00`
не пересекаются.

| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |

| ------------------------ | -------------------------------------------------------------------------------------------- |

| `maxDurationMinutes`     | Кратно шагу, ≥ min, ≤ 720                                                                    |

| `isActive`               | Неактивные ресурсы не принимают новых броней и скрыты от участников                          |

| `createdAt`, `updatedAt` |                                                                                              |

### 3.4. Рабочие часы [MVP]

Хранятся в отдельной таблице: `resource_id`, `weekday` (ISO: 1 = понедельник … 7 = воскресенье), `openTime`,
`closeTime` (локальное `time`, без даты и без зоны).

- **[MVP]** Не более одного интервала на день недели: `unique(resource_id, weekday)`. Отсутствие дня недели
  означает, что ресурс в этот день закрыт.
- `openTime < closeTime`. Окна, переходящие через полночь, не поддерживаются.
- `openTime` и `closeTime` должны лежать на сетке слотов. Сетка отсчитывается в минутах от локальной полуночи,
  поэтому `closeTime − openTime` кратно шагу.
- **[Post-MVP]** Несколько интервалов в день (обеденный перерыв), исключения по датам (праздники, закрытие на обслуживание).

### 3.5. Booking [MVP]

| Поле                     | Правила                                                        |
| ------------------------ | -------------------------------------------------------------- |
| `id`                     | UUID                                                           |
| `resourceId`             | FK → Resource                                                  |
| `userId`                 | FK → User (владелец)                                           |
| `title`                  | Обязательное, 1–100 символов, trim                             |
| `startAt`, `endAt`       | `timestamptz`, моменты в UTC; в БД `CHECK (start_at < end_at)` |
| `status`                 | `confirmed` \| `cancelled`                                     |
| `cancelledAt`            | Устанавливается при отмене                                     |
| `cancelledById`          | FK → User; может отличаться от владельца (отмена админом)      |
| `createdAt`, `updatedAt` |                                                                |

Брони никогда не удаляются. Отмена — это смена статуса, что сохраняет историю и аудит.

**Гарантия отсутствия пересечений на уровне БД:**

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings ADD CONSTRAINT bookings_no_overlap
  EXCLUDE USING gist (
    resource_id WITH =,
    tstzrange(start_at, end_at, '[)') WITH &&
  ) WHERE (status = 'confirmed');
```

Использовать две обычные колонки плюс range-_выражение_ в ограничении, а не колонку типа `tstzrange`. Prisma
нативно моделирует колонки `DateTime`, а range-колонка была бы `Unsupported(...)`. Проверить это в задаче M4.

## 4. Модель времени

Самая коварная часть домена. Каждое правило ниже требует unit-теста.

1. API работает в **UTC ISO 8601** (`2026-11-18T09:00:00Z`). БД хранит `timestamptz`.
2. Параметр `date` (`YYYY-MM-DD`) всегда означает **локальную календарную дату в часовом поясе ресурса**.
3. **Рабочее окно для даты.** Перевести `date + openTime` и `date + closeTime` из часового пояса ресурса
   в UTC-моменты `openAt` и `closeAt`.
4. **Сетка.** Слоты генерируются шагами в **абсолютном времени** от `openAt` с шагом `slotStepMinutes`,
   пока `slot.end ≤ closeAt`. Допустимое начало брони — `openAt + k·step`.
5. **DST.** Переходы на летнее/зимнее время обычно происходят ночью, вне рабочих часов, поэтому сетку не затрагивают.
   Если переход попадает внутрь окна (например, у круглосуточных ресурсов), шаги в абсолютном времени сохраняют
   длину каждого слота ровно `step`, а день становится на час короче или длиннее. Локальные метки показывают скачок
   (`01:30 → 03:00`). Если `openTime` или `closeTime` — несуществующее локальное время (разрыв при переводе часов
   вперёд), сдвинуть его вперёд к первому валидному моменту. Для неоднозначного локального времени (перевод назад)
   использовать более ранний offset. Это соответствует стратегии `compatible` в Temporal и date-fns-tz. Тест-кейсы:
   `Europe/Berlin` в последнее воскресенье марта и октября; одна зона без DST (`Asia/Tokyo`).
6. **Одно окно на бронь.** Бронь должна лежать внутри **одного** рабочего окна. Она не может охватывать два
   дня, даже если ресурс открыт 00:00–24:00 в оба дня.
7. **Сейчас.** Бизнес-правила используют серверное время через внедряемый `Clock`, чтобы в тестах можно было
   заморозить время. Клиент показывает время в **часовом поясе ресурса** с подписью зоны. Если он отличается
   от зоны браузера, дополнительно показывается локальное время пользователя.

## 5. Сценарии использования и бизнес-правила

### 5.1. Аутентификация [MVP]

- **Регистрация.** `email`, `password`, `name`. Если email занят — вернуть `409 email-taken`.
  - Осознанный компромисс: это раскрывает факт существования аккаунта. Смягчается rate limiting ([Post-MVP]).
- **Вход.** Неверный email и неверный пароль дают одну и ту же ошибку (`401 invalid-credentials`), и ответ
  занимает примерно одинаковое время в обоих случаях. Если пользователь не найден, всё равно хешировать фиктивный пароль.
- **Токены.**
  - Access JWT: TTL 15 мин. Claims: `sub`, `role`. Клиент хранит его только в памяти.
  - Refresh-токен: случайная непрозрачная строка, TTL 30 дней, передаётся в cookie с `HttpOnly`, `Secure`,
    `SameSite=Strict` и `Path=/auth`.
- **Refresh.** Каждый refresh **ротирует** токен: старый отзывается, новый выдаётся в той же семье.
  - **Обнаружение повторного использования.** Если отозванный токен предъявлен снова — отозвать всю семью.
    Пользователь должен войти заново.
  - Параллельные refresh из двух вкладок браузера — реальная проблема. Клиент обязан дедуплицировать
    refresh-запросы, находящиеся в полёте. Опционально на сервере: короткий grace period для только что ротированного токена.
- **Логаут.** Отзывает семью текущего токена и очищает cookie. Логаут идемпотентен.
- **`GET /me`.** Возвращает текущего пользователя.
- **[Post-MVP]**
  - Выход со всех устройств.
  - Сброс пароля по email.
  - Rate limiting входа (Redis).
  - Подтверждение email.

### 5.2. Ресурсы [MVP]

- **Список.**
  - Фильтры: `type`, `minCapacity`, `q` (подстрока имени, без учёта регистра).
  - Пагинация: `page`, `pageSize` (по умолчанию 20, максимум 100). Ответ содержит `total`.
  - Сортировка: по `name`.
  - Участники видят только активные ресурсы. Админы могут фильтровать по `isActive`.
- **Детальная.** Включает рабочие часы. Участник, запросивший неактивный ресурс, получает `404`, что не
  раскрывает факт его существования.
- **Создание / изменение (админ).** Применяются все правила из 3.3–3.4. Изменение — с семантикой PATCH.
- **Влияние изменений на существующие брони.**
  - Изменение часов, шага, длительностей или часового пояса **не** затрагивает существующие брони. Они —
    абсолютные моменты и остаются валидными.
  - Новые правила применяются только к новым броням.
  - UI предупреждает админа, если есть будущие брони вне новых часов.
- **Удаление (админ).**
  - Ресурс без единой брони удаляется физически.
  - Иначе вернуть `409 resource-has-bookings` и предложить деактивацию.
- **Деактивация (админ).**
  - Существующие будущие брони остаются. Ничего не отменяется автоматически.
  - Ответ содержит `futureBookingsCount`, чтобы админ мог принять решение.
  - **[Post-MVP]** «Деактивировать и отменить будущие брони» с уведомлением владельцев.

### 5.3. Доступность [MVP]

`GET /resources/:id/availability?date=YYYY-MM-DD`

- Допустимые даты: от **сегодня** (в tz ресурса) до **сегодня + bookingHorizonDays**. Иначе вернуть
  `422 date-out-of-range`.
- **Ответ:**

  ```jsonc
  {
    "date": "2026-11-20",
    "timezone": "Europe/Berlin",
    "isClosed": false,
    "openAt": "2026-11-20T08:00:00Z",
    "closeAt": "2026-11-20T17:00:00Z",
    "slotStepMinutes": 30,
    "minDurationMinutes": 30,
    "maxDurationMinutes": 240,
    "slots": [
      { "startAt": "...", "endAt": "...", "status": "free" | "booked" | "mine" | "past" }
    ]
  }
  ```

- **Статусы слотов.**
  - `past`: `slot.startAt ≤ now`.
  - `mine`: слот покрыт подтверждённой бронью текущего пользователя.
  - `booked`: слот покрыт чужой подтверждённой бронью.
  - `free`: любой другой слот.
- **Представление для админа.** Админы дополнительно получают `bookings: [{ id, startAt, endAt, title, user: { id, name } }]`.
  Участники не получают данных других пользователей.
- **Ни к чему не обязывает.** Доступность — это снимок. Настоящая проверка происходит при создании (см. 5.4, шаг 6).
- **[Post-MVP]** Вид на несколько дней/неделю, кеш в Redis с инвалидацией при изменении броней, live-обновления через SSE.

### 5.4. Создание брони [MVP]

`POST /bookings { resourceId, startAt, endAt, title }`

Порядок валидации. У каждого шага своя ошибка, перечислены в разделе 7.

1. **DTO.** Типы полей, ISO-моменты, длина title → `400 validation-error`.
2. **Ресурс.** Существует и активен → `404 resource-not-found`. Для участников неактивный считается
   ненайденным; админы получают `422 resource-inactive`.
3. **Правила времени:**
   - `startAt > now` → `422 booking-in-past`;
   - `startAt ≤ now + bookingHorizonDays` → `422 booking-beyond-horizon`;
   - `[startAt, endAt)` лежит внутри одного рабочего окна, то есть ресурс в этот день открыт →
     `422 outside-working-hours`;
   - `startAt` и `endAt` на сетке слотов → `422 not-aligned-to-slot`;
   - `min ≤ duration ≤ max` → `422 invalid-duration`.
4. **Лимит на пользователя.** У пользователя меньше `MAX_ACTIVE_BOOKINGS_PER_USER` (конфиг, по умолчанию 5)
   активных броней → `422 booking-limit-reached`. На админов не распространяется.
5. **Insert** со `status = confirmed`.
6. **Пересечение.**
   - Exclusion constraint отклоняет insert с SQLSTATE `23P01` → `409 booking-conflict`.
   - Приложение **не** делает предварительную проверку пересечений через SELECT. Такая проверка подвержена
     гонкам, а гарантию даёт ограничение.
   - Тело ответа 409 сообщает клиенту, что нужно перезапросить доступность.

**Конкурентность.**

- **Два пользователя, один слот, один момент.** Ровно один получает `201`, другой — `409`. Интеграционный
  тест на реальном Postgres запускает N параллельных запросов и проверяет это.
- **Гонка по лимиту на пользователя.** Пользователь с `limit − 1` бронями отправляет два запроса параллельно.
  Наивное «посчитать, потом вставить» пропустит оба.
  - Шаги 4–5 выполняются в одной транзакции.
  - В её начале: `SELECT ... FROM users WHERE id = $1 FOR UPDATE`. Это сериализует запросы на бронирование
    одного пользователя.
  - Альтернативы для ADR: `pg_advisory_xact_lock(userId)` или уровень изоляции `SERIALIZABLE` с
    повтором.
- **Двойная отправка.** Пользователь кликает дважды. Второй запрос получает `409` от ограничения — это
  корректное поведение. **[Post-MVP]** Заголовок `Idempotency-Key`.

### 5.5. Мои брони [MVP]

`GET /bookings?scope=upcoming|past&status=confirmed|cancelled&page=&pageSize=`

| Scope      | Выборка                               | Сортировка     |
| ---------- | ------------------------------------- | -------------- |
| `upcoming` | `endAt > now` (включая идущие сейчас) | `startAt ASC`  |
| `past`     | `endAt ≤ now`                         | `startAt DESC` |

- Всегда только брони текущего пользователя, в том числе для админов.
- Каждый элемент содержит краткую информацию о ресурсе (`id`, `name`, `type`, `timezone`) и флаг `canCancel`,
  вычисленный сервером.
- **[Post-MVP]**
  - Админ: все брони с фильтрами по ресурсу, пользователю и диапазону дат.
  - Экспорт в iCal.

### 5.6. Отмена брони [MVP]

`POST /bookings/:id/cancel`

- Бронь не найдена, или участник запрашивает чужую → `404 booking-not-found`. Ответ не раскрывает факт
  существования брони.
- **Уже отменена.** Вызов **идемпотентен**: `200` с текущим состоянием. Это делает безопасными оптимистичный
  UI и повторы.
- **Бронь закончилась** (`endAt ≤ now`) → `422 booking-already-finished`.
- **Дедлайн для участника.** Участник может отменить только пока `now < startAt − CANCELLATION_CUTOFF_MINUTES`
  (конфиг, по умолчанию 60) → `422 cancellation-window-closed`.
- **Админы** могут отменить любую незакончившуюся бронь, включая идущую сейчас.
- **При успехе:** `status = cancelled`, установить `cancelledAt`, `cancelledById`. Слот сразу освобождается,
  так как ограничение покрывает только `confirmed`.
- **[Post-MVP]**
  - Причина отмены.
  - Уведомление владельца при отмене админом.
  - «Завершить досрочно» для идущей брони: сократить `endAt` до границы текущего слота.

### 5.7. Post-MVP функции (целевое состояние)

Перечислены здесь, чтобы дизайн MVP оставил для них место. Обязательств по реализации пока нет.

| Функция                           | Заметки / влияние на дизайн                                                                                                                                                          |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Перенос брони                     | `PATCH /bookings/:id` с новым периодом. Изменение проверяется тем же exclusion constraint. Применяются правила дедлайна.                                                             |
| Временный hold                    | Выбор слота создаёт бронь `held` с `expiresAt` (5 мин). Она входит в ограничение (`status IN ('confirmed','held')`). Освобождается отложенной задачей BullMQ или ленивым истечением. |
| Повторяющиеся брони               | Правило (еженедельно, N раз) разворачивается в отдельные брони. Частичные конфликты: всё-или-ничего либо «забронировать свободное» (продуктовое решение).                            |
| Напоминания                       | Задача BullMQ за N минут до начала: email или in-app.                                                                                                                                |
| Live-доступность                  | SSE-поток на ресурс и дату; инвалидирует кеш TanStack Query.                                                                                                                         |
| Кеш доступности                   | Redis, ключ `resource:date`, инвалидация при создании или отмене.                                                                                                                    |
| Праздники / закрытия              | Исключения по датам поверх недельного расписания.                                                                                                                                    |
| Количество участников             | Проверка `attendees ≤ capacity` при создании.                                                                                                                                        |
| Управление пользователями админом | Смена ролей, деактивация пользователей (с отзывом их сессий).                                                                                                                        |
| Журнал аудита                     | Кто что менял в ресурсах и бронях.                                                                                                                                                   |
| Rate limiting                     | Эндпоинты аутентификации и создание броней.                                                                                                                                          |

## 7. Ошибки

Все ошибки — RFC 9457 Problem Details (`Content-Type: application/problem+json`):

```json
{
  "type": "/problems/booking-conflict",
  "title": "Booking conflict",
  "status": 409,
  "detail": "The selected time overlaps an existing booking.",
  "instance": "/bookings",
  "code": "booking-conflict"
}
```

- `code` — машиночитаемый ключ, который фронтенд маппит на сообщения в UI.
- Ошибки валидации содержат `errors: [{ field, message }]`, которые фронтенд маппит на поля формы.
  `field` — путь через точку для вложенных полей: `workingHours.0.openTime`.
- Ошибки вне списка доменных кодов ниже (неизвестный маршрут, некорректный JSON, сбой сервера)
  получают `code`, выведенный из HTTP-статуса: `not-found`, `bad-request`, `internal-server-error`.
- `detail` содержит только текст, написанный нами намеренно. Сообщения фреймворка и исходные ошибки
  в ответ не попадают: они могут отражать входные данные запроса или раскрывать внутренности.

Соглашение по статус-кодам:

| Статус | Когда                                                                                                      |
| ------ | ---------------------------------------------------------------------------------------------------------- |
| `400`  | Некорректный запрос / не прошла валидация DTO                                                              |
| `401`  | Не аутентифицирован (нет или истёк access-токен, неверные учётные данные)                                  |
| `403`  | Аутентифицирован, но нет прав (например, участник вызывает админский эндпоинт)                             |
| `404`  | Не найдено **или скрыто от этого пользователя**                                                            |
| `409`  | Конфликт с текущим состоянием другой сущности (`booking-conflict`, `email-taken`, `resource-has-bookings`) |
| `422`  | Запрос корректен, но нарушает бизнес-правило                                                               |
| `500`  | Непредвиденная ошибка; ответ не содержит внутренностей, подробности логируются с request id                |

| Код                                                                                                                                                                                                                                          | Статус |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| `validation-error`                                                                                                                                                                                                                           | 400    |
| `invalid-credentials`, `unauthorized`, `refresh-token-invalid`                                                                                                                                                                               | 401    |
| `forbidden`                                                                                                                                                                                                                                  | 403    |
| `resource-not-found`, `booking-not-found`                                                                                                                                                                                                    | 404    |
| `email-taken`, `booking-conflict`, `resource-has-bookings`                                                                                                                                                                                   | 409    |
| `resource-inactive`, `booking-in-past`, `booking-beyond-horizon`, `outside-working-hours`, `not-aligned-to-slot`, `invalid-duration`, `booking-limit-reached`, `booking-already-finished`, `cancellation-window-closed`, `date-out-of-range` | 422    |

## 8. Поведение фронтенда [MVP]

- **Аутентификация.**
  - При загрузке приложения тихо вызвать `POST /auth/refresh`, чтобы восстановить сессию.
  - При `401` на любой запрос выполнить один дедуплицированный refresh и повторить запрос. Если refresh
    не удался — редирект на логин с возвратом на исходный URL после входа.
- **Список ресурсов.**
  - Фильтры и номер страницы живут в search params URL, поэтому состояние переживает перезагрузку и переходы назад/вперёд.
  - Состояния загрузки, пустого списка и ошибки.
- **Страница ресурса.**
  - Выбор даты, ограниченный горизонтом бронирования, и сетка дня в часовом поясе ресурса.
  - Пользователь выбирает начальный слот и длительность. Предлагаются только допустимые длительности: в пределах
    min/max и не пересекающие занятый слот или конец окна.
  - При `409`: показать сообщение, перезапросить доступность и сохранить значения формы.
- **Мои брони.**
  - Вкладки «предстоящие» и «прошедшие».
  - Отмена с оптимистичным обновлением. При ошибке — откат и показ `detail` из problem.
  - Кнопка отмены показывается только при `canCancel = true`.
- **Админка.**
  - Форма ресурса с рабочими часами по дням недели.
  - Валидация повторяет серверные правила (Zod), но источником истины остаётся сервер.
- **Ошибки.** Единый маппинг `code → сообщение` с fallback на `title`/`detail` для неизвестных кодов.

## 10. Обязательные тесты бизнес-правил

- **Модель времени (unit, замороженные часы).**
  - Генерация сетки.
  - Дни перехода DST в `Europe/Berlin`; зона без DST.
  - Несуществующее `openTime`.
  - Бронь отклоняется на границах окна: начинается в `close`, заканчивается в `close + step`.
  - Бронь принимается ровно на `[open, open+min)` и `[close−max, close)`.
- **Полуоткрытые периоды.** Соседние брони разрешены; пересечение в 1 минуту отклоняется.
- **Конкурентность (интеграционные, реальный Postgres).**
  - N параллельных созданий на один слот → ровно 1 × `201`.
  - Параллельные создания от одного пользователя при `limit − 1` → успешно ровно одно.
- **Отмена.**
  - Граница дедлайна: ровно в `startAt − cutoff` → отклоняется.
  - Идемпотентная повторная отмена.
  - Отменённый слот можно забронировать снова.
- **Авторизация.**
  - Участник не может увидеть или отменить чужую бронь (`404`).
  - Участник получает `403` на админских эндпоинтах.
- **Аутентификация.** Ротация refresh; повторно использованный refresh-токен отзывает всю семью.
